# 共通部分構造の発見：小構造の切り出し・照合・集計 v0.1

本メモは、`knowhow-graph-0.1`の構造化JSONから共通部分構造を発見するための初期実装案を整理したものである。記載した疑似コードは処理の説明であり、実装済みコードではない。

関連資料：[構造化後の処理フローと研究根拠 v0.1](構造化後の処理フローと研究根拠_v0.1.md) ／ [構造化Systemプロンプト v0.1](../prompts/knowhow-structure-system-v0.1.txt)

## このメモの範囲

現行JSONなら、まずは**「各事例から小さな構造を切り出す → 属性と接続が同じものを集める → 出現事例と対応表を保存する」**方法で実装できます。

ここでは、原理の説明文を作る前段階である、**共通部分構造を発見する処理**に絞って説明します。

### 処理の見取り図

```text
構造化JSON
    → 検査・グラフ化
    → CLAIMが1〜2個の断片を切り出す
    → 未解決の意味に依存する断片を保留する
    → 安価な特徴で候補を絞る
    → 属性付きグラフ同型判定で照合する
    → パターン・出現事例・対応表・根拠を保存する
```

| 段階 | 得られるもの | まだ判断しないこと |
| --- | --- | --- |
| 候補の絞り込み | ノード数・属性の内訳などが同じ断片群 | 接続まで一致するか |
| 厳密な照合 | 指定した属性と有向接続が一致する構造・対応表 | 原文解釈や対象の置換が妥当か |
| 出現の集計 | 同じパターンを持つ事例と根拠 | 普遍的な原理や転用可能性 |

機械的な一致は、採用した表現・照合規則の下での一致です。原理候補としての採否や質問への適用は、原文と条件を確認する後続工程で扱います。

## 1. 何を同じとみなすかを決める

最初に、比較に使う情報を固定します。

| 情報 | 初期実装での扱い |
| --- | --- |
| ノードの`type` | 一致が必要 |
| 操作・量・状態の`concept_id` | 正規化済みの概念が一致すること |
| CHANGEの`direction` | 一致が必要 |
| CLAIMの`predicate` | 一致が必要 |
| `polarity`・`modality`・`context` | 一致が必要 |
| 接続の`role`と向き | 一致が必要 |
| 条件、AND・OR・NOT、比較値・単位 | 保持して比較する |
| ノードID・原文引用 | 一致判定には使わず、根拠として保存 |
| ENTITYの具体名 | 許可した対象について変数として扱う |

例えば、「説明」と「段取り替え」は異なる活動ですが、両方に接続された量が`activity_duration`なら、対象を対応づけた共通構造を探せます。

ただし、**異なるENTITYを一つに潰してはいけません。** 元のグラフで別の対象なら別の変数にし、同じ対象への参照は同じ変数を使います。

未登録のACTIONやQUANTITYなどは、`concept_id: null`同士だからという理由で一致させません。該当部分は意味の比較を保留します。

## 2. CLAIMを起点に、意味が欠けない単位で切り出す

現行JSONでは、意味関係が`CLAIM`ノードになっています。そこで、各CLAIMを起点に必要なノードをたどります。

例えば、

> 説明にかかる時間の増加によって、実作業に使える時間が減ることがある。

から切り出す単位は、次の全体です。

```text
CLAIM
  predicate: CAUSES
  modality: POSSIBLE
  │
  ├─ FROM → CHANGE[INCREASE]
  │            └─ QUANTITY → QUANTITY[activity_duration]
  │                              └─ BEARER → ENTITY[説明]
  │
  └─ TO → CHANGE[DECREASE]
               └─ QUANTITY → QUANTITY[available_duration]
                                 └─ BEARER → ENTITY[実作業]
```

この切り出しには、次の規則を設けます。

- CLAIMを含めたら、`FROM`・`TO`を含める。
- CHANGEを含めたら、変化するQUANTITYとそのBEARERを含める。
- ACTIONを含めたら、明示されたTARGETやAGENTなどを含める。
- STATEを含めたら、SUBJECTを含める。
- 条件があれば、`CONDITION`以下を含める。
- LOGICを含めたら、その全要素を含める。

**`CAUSES → CHANGE`だけを切り出して、量や条件を捨てた一致を作らないための規則**です。

原文全体から見ると部分構造ですが、その中の各記述は意味を保った単位にします。

## 3. 最初は「CLAIMが1個」と「CLAIMが2個」を列挙する

最初から任意の大きさの部分グラフをすべて探す必要はありません。

まず、各事例について次を取り出します。

```text
CLAIMが1個の構造
  ・AがBを引き起こす
  ・AがBの手がかりになる
  ・AにはBが必要
  など

CLAIMが2個でつながった構造
  ・A → B → C
  ・A → B、A → C
  ・A → C、B → C
  など
```

これは、共通原理のテンプレートを先に決めることではありません。**探索する大きさだけを制限し、その範囲にある構造を列挙する**方法です。

CLAIM同士のつながりは、必要な引数まで含めた構造がノードを共有しているかで判断できます。例えば、最初の関係の結果が、次の関係の原因として同じCHANGEノードを参照していれば、連鎖として取り出せます。

ここでいう「1個・2個」はCLAIMの数です。対象・量・条件を含めるため、実際のノード数はもっと多くなります。

## 4. 似た候補をまとめてから、正確に同じ構造か確認する

切り出した構造同士の照合は、二段階にすると実装しやすくなります。

まず、安価に計算できる特徴で候補を分けます。

```text
ノード数
接続数
ノード型ごとの数
概念IDごとの数
predicateごとの数
roleごとの数
```

例えば、ノード数や概念の内訳が違う構造は、今回の厳密な一致条件では同じになりません。そこで、同じ特徴を持つ構造だけを詳しく照合します。

次に、**属性付きのグラフ同型判定**を行います。

これは、

> ノード名を付け替えたときに、比較対象の属性・接続・向きがすべて一致するか。

を調べる処理です。ここで、パターン側と事例側のノード対応も得ます。

PythonならNetworkXの同型判定が候補になります。ただし、標準設定ではノード・接続の属性を比較しないため、**`concept_id`や`role`などを比較する条件を明示する必要があります。** [NetworkX公式ドキュメント](https://networkx.org/documentation/stable/reference/algorithms/generated/networkx.algorithms.isomorphism.is_isomorphic.html)

現行JSONでは同じノード間に異なるroleの接続があり得るため、実装では、それらを保持できる有向グラフ表現を使います。

## 5. 一致した構造を、一つのパターンとして集計する

例えば、次の二つの仮想事例があるとします。

```text
事例A：
説明にかかる時間の増加
  → 実作業に使える時間の減少

事例B：
段取り替えにかかる時間の増加
  → 製造に使える時間の減少
```

不確実性なども一致していれば、次のパターンにまとめられます。

```text
パターンP001：

活動Xにかかる時間の増加
  → 活動Yに使える時間の減少
```

保存するのは、説明文だけではありません。

```text
P001
  共通部分グラフ
  使用した照合規則・辞書バージョン

  出現事例A
    X → 説明
    Y → 実作業
    各ノード・接続の対応表
    原文根拠

  出現事例B
    X → 段取り替え
    Y → 製造
    各ノード・接続の対応表
    原文根拠
```

同じ事例に何回現れても、支持事例数としては原則1件です。出現回数と事例数を別々に数えます。

一方、次の事例は同じパターンにしません。

```text
説明にかかる時間の増加
  → 実作業にかかる時間の減少
```

結果側が`available_duration`ではなく`activity_duration`だからです。形と増減が同じでも、量の意味が異なります。

## 6. 処理全体は、次のようなループになる

以下は実装の流れを示す疑似コードです。

```python
for document in documents:
    graph = validate_and_build_graph(document)

    fragments = extract_fragments(
        graph,
        max_claims=2,
        preserve_arguments=True,
        preserve_conditions=True
    )

    for fragment in fragments:
        if has_unresolved_required_meaning(fragment):
            save_for_review(fragment)
            continue

        key = coarse_signature(fragment)

        pattern, mapping = find_exact_match(
            fragment,
            patterns_in_bucket[key],
            matching_policy
        )

        if pattern is None:
            pattern, mapping = register_new_pattern(fragment, key)

        save_occurrence(
            pattern,
            document,
            mapping,
            original_evidence=fragment.evidence
        )

candidates = patterns_supported_by_at_least_two_documents()
```

`coarse_signature`は候補を減らすための特徴です。それが同じだけでは一致と確定せず、`find_exact_match`で属性と接続を確認します。

この方法では、**各断片を、同じ特徴を持つパターンの代表と照合**します。ノウハウ全件のペアをLLMへ渡す必要はありません。プログラムによる小構造の比較は行います。

## 7. 条件が異なるものは、別の扱いにする

最初は、条件を含めた厳密な一致から始めると結果を確認しやすくなります。

その後、探索範囲を広げる場合は、次の二種類を分けます。

| 種類 | 判定 |
| --- | --- |
| 条件を含む共通構造 | 条件の構造・属性も照合した |
| 共通コアの候補 | 中心の構造は一致するが、条件に差や未解決部分がある |

後者でも、各事例の条件を削除せず、差分として保存します。構造に条件が書かれていないことも、「無条件で成立する」という意味にはしません。

## 8. 小さな構造で不足したら、探索を拡張する

小構造の集計で必要な共通性を拾えるか確認した後、CLAIMを3個以上へ広げます。より一般的な頻出部分グラフ探索には、gSpanなどの手法があります。[Yan & Han（2002）, gSpan](https://sites.cs.ucsb.edu/~xyan/papers/gSpan-short.pdf)

ただし、CLAIMの引数を必ず含める規則や、条件の保持、対象の変数化は、今回の用途に合わせた処理が必要です。また、断片の数や同じ特徴を持つ候補が増えれば、照合時間も増えます。

まず実装する範囲は、**「CLAIM1〜2個の切り出し」「属性付き同型判定」「パターン別の出現事例・対応表の保存」**です。ここまでで、どの事例にどの共通部分があるかを、プログラムで一覧化できます。
