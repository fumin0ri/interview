# 異分野の熟練者ノウハウから共通原理を発見・活用する設計案

作成日：2026-09-10

## 目的と位置付け

目指すのは、**質問の分野がDBに存在しなくても、異分野の熟練者ノウハウから使える考え方を取り出し、適用条件とともに回答するシステム**である。

全体を、次の二つの処理に分ける。

| 処理 | 目的 | 主な出力 |
| --- | --- | --- |
| 事前処理 | DB内のノウハウから共通原理を発見する | 共通原理候補・成立条件・原文根拠 |
| 質問時の処理 | 原理を質問の対象分野へ適用する | 使える考え方・具体的な確認方法・根拠 |

> 本文は現時点の設計案であり、実データで検証しながら調整する。既存システムの実装済み仕様や、実験で確認された結果を示すものではない。

## 1. 全体の流れ

### 事前処理：ノウハウから原理を発見する

```text
原文ノウハウ
    │
    ├─ ① 根拠を残して構造化
    ▼
条件・行動・状態変化・結果・推奨を表すグラフ
    │
    ├─ ② 比較する候補を集める
    ▼
異分野を含むノウハウのペア
    │
    ├─ ③ 部分構造を対応付ける
    ▼
共通部分・相違点・対応表
    │
    ├─ ④ 他の事例でも成立するか照合する
    ▼
共通構造と、それを支持する事例群
    │
    ├─ ⑤ 共通構造を言語化する
    ▼
共通原理候補 ＋ 成立条件 ＋ 原文根拠
```

### 質問時：原理を対象分野へ適用する

```text
質問
    │
    ├─ ⑥ 事実・目的・制約・未知部分を構造化
    ▼
未完成の質問グラフ
    │
    ├─ ⑦ 事例・原理候補を検索する
    ├─ ⑧ 質問との対応と適用条件を確認する
    ▼
適用仮説・矛盾・不足情報
    │
    ├─ ⑨ 回答する
    ▼
使える考え方 ＋ 具体的な確認方法 ＋ 根拠
```

**共通原理がまだ見つかっていない事例も検索対象に残す。** 質問から元事例へ直接アクセスし、適用仮説を作る経路も持たせる。

## 2. 原文の主張を保つ構造化

最初の構造化では、原文が何を主張しているかを保存する。

### 抽出例

次のノウハウを例に考える。

> 遅れているプロジェクトに途中から人員を追加すると、説明・調整時間が増え、実作業時間が減って、さらに遅れることがある。

| 要素 | 抽出する内容 |
| --- | --- |
| 条件 | プロジェクトが遅れている |
| 行動 | 途中から人員を追加する |
| 状態変化 | 説明・調整時間が増加する |
| 次の状態変化 | 実作業時間が減少する |
| 結果 | 遅延が悪化する |
| 不確実性 | 必ずではなく「ことがある」 |
| 根拠 | 各要素に対応する原文の箇所 |

### 比較用の表現

**対象となる量と、その変化を分ける。**

```text
行動：人員を追加
    → 変化：説明・調整時間が増加
    → 変化：実作業時間が減少
    → 変化：遅延の程度が増加
```

実装時には、増減表現をそろえ、「行動または状態変化の間の関係」として表す案とする。

### 保持する区別

- 「時間が減ると遅延が増える」を、勝手に「時間を増やせば遅延が減る」へ変換しない。
- 目的や推奨が原文にない場合は、未記載にする。
- **原文明示・表現の正規化・追加推論を区別する。**

この区別が、後の構造比較と検証の土台になる。

## 3. 比較候補の検索

全件同士の比較はデータ量が増えると重くなるため、先に比較候補を絞る。

### 候補を集める観点

| 観点 | 比較する内容 |
| --- | --- |
| 原文の意味 | 原文の意味が近いか |
| 目的・作用 | 業界用語を抽象化した目的・作用の説明が近いか |
| 関係構造 | 関係の種類や組み合わせが近いか |

> この段階の検索結果は、「同じ原理を持つ」と判定された結果ではなく、詳しく比較する対象である。

### 小規模検証での進め方

初期は全ペアを比較し、構造比較が機能することを確認してから候補検索を導入する。これにより、**検索の取りこぼしと構造比較の失敗を分けて評価できる。**

## 4. 部分構造の対応付け

LLMに二つの事例の対応候補を出させ、対応する部分と意味の違いを確認する。

```text
事例Aの行動       ↔ 事例Bの行動
事例Aの中間変化   ↔ 事例Bの中間変化
事例Aの結果       ↔ 事例Bの結果
```

### プログラム側で確認すること

- 対応先が矛盾していないか。
- 関係の向きや増減が整合するか。
- 対応した関係がつながっているか。
- どの部分が一致し、どの部分が一致しないか。

ただし、**グラフの形が一致しただけでは、同じ原理とは判断しない。** 目的との関係、作用の意味、成立条件も比較する。

### この段階の出力

類似度の点数だけでなく、次を保存する。

| 出力 | 内容 |
| --- | --- |
| 対応表 | 対応したノード・関係 |
| 共通部分 | 共通する部分構造 |
| 相違点 | 一致しない部分・矛盾 |
| 追加仮定 | 対応付けに必要な仮定 |
| 根拠 | それぞれの原文の対応箇所 |

プログラムで確認できるのは構造上の整合性であり、原文の因果説明の正しさや、他分野での成立そのものまでは保証できない。

## 5. 共通原理候補の抽出

ペアから見つけた共通部分が、別の事例にもあるか調べる。

### 集約する単位

**事例全体を一つのクラスタにまとめることより、同じ部分構造を支持する事例を集めることを重視する。** 一つの事例が複数の原理を支持していてもよい。

AとB、BとCが似ていても、三つに同じ共通原理があるとは限らない。そのため、共通部分を直接確認する。

### 原理候補として保存する情報

| 項目 | 内容 |
| --- | --- |
| 共通構造 | 事例間で対応した関係 |
| 原理の説明 | 共通構造を自然言語で説明したもの |
| 成立条件 | どんな状況で使えそうか |
| 判断への示唆 | 何を観察し、どう考えるか |
| 支持事例 | 元ノウハウと対応箇所 |
| 未確認部分 | 根拠が不足している解釈や適用範囲 |

例えば、根拠が「資源追加によって別の負荷が増えた」までなら、その範囲で原理を表現する。「ボトルネック原理」と呼ぶには、処理能力の上限などの根拠も必要になる。

> 複数事例の共通性は原理候補の根拠になるが、普遍的な法則の証明にはならない。

## 6. 質問への適用

質問は情報が欠けた状態で来るため、既知の事実と未知部分を分ける。原理は、**未知部分を埋める仮説**として利用する。

### 質問と適用仮説の例

**質問：**

> 受付スタッフを増やしたのに、入場待ちが改善しない。

この質問から、後工程の混雑を事実として追加してはいけない。異分野のノウハウを参考に、次の仮説を生成し、その条件を確認する。

**適用仮説：**

> 受付以降に処理が滞る工程があるのではないか。

### 最終回答に含める情報

| 要素 | 内容 |
| --- | --- |
| 使える考え方 | 異分野から取り出した原理 |
| 質問への対応 | 何が何に当たると考えたか |
| 適用条件 | どんな場合に使えるか |
| 確認方法 | 不足情報をどう確かめるか |
| 根拠 | 参照したノウハウ |

これにより、もっともらしい類推だけでなく、ユーザーが検証できる回答を目指す。

## 7. 評価方法と最初の実装範囲

### 途中の処理と最終回答を分けて評価する

| 評価対象 | 確認すること |
| --- | --- |
| 構造化 | 原文の関係・条件・不確実性を保てたか |
| 構造比較 | 同じ原理の事例と、形だけ似た事例を区別できたか |
| 原理抽出 | 原文を超えた一般化をしていないか |
| 検索 | 有効な異分野事例・原理が上位に出たか |
| 回答 | 原理を具体化し、適用条件と確認方法を示せたか |

### 最終評価の条件

ノウハウ1件の除外に加えて、**対象分野全体をDBから除外する評価**を行う。除外事例を使って作った原理や要約も残さない。

回答は、次の3方式で比較する。

1. 検索なし
2. 通常の意味検索
3. 提案手法

元クラスタの再現だけでなく、人が判断した転用の妥当性を評価する。

### 最初の実装範囲

最初は、**少数の原文を構造化し、事例ペアの共通部分と相違点を根拠付きで出すところまで**とする。

```text
少数の原文
    → 根拠付きの構造化
    → 全ペアの構造比較
    → 共通部分・相違点・追加仮定・原文根拠
```

ここで意味のある共通構造を見つけられるかが、後の原理抽出と検索を支える最初の検証点になる。
